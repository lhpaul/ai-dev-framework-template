## Summary

**Approach**: Execute the existing PR-Agent image through a template-owned Python launcher that installs a narrow runtime patch before invoking the original action runner. Defer premature history-first truncation until GitHub publication, where a fitter preserves the current visible review and removes history before considering a notice. The decision contract below is the authoritative algorithm; other sections reference it.

**Estimated complexity**: M — integration with a third-party runtime, persistent comment updates, consumer sync and boundary tests require more than a Fast Track patch.

**Dependencies**: Spec PR #1954 is merged. No other work item is required. Docker is required for the runtime compatibility smoke test; ordinary unit tests use Python's standard library. At implementation start, verify that the approved spec is available on the implementation base and that GitHub still records #1954 as merged. If either check fails or cannot be verified, stop before implementation edits until the approved dependency is restored or the missing evidence is resolved.

## Layer-by-Layer Changes

### Runtime and Publication Decision Contract

The pure fitter accepts a fully composed review body and a positive integer limit. The launcher supplies the GitHub provider's existing limit. Unsupported limit types/values raise an explicit error rather than producing a publishable clean review.

1. A complete body at or below the limit returns exactly as received, before any parsing or normalization.
2. For oversized review bodies, use the producer's state parser/splitter. A complete valid state block can be retained only in its entirety. Remove the resolved-history suffix only when it is the exact suffix produced by `_render_resolved_section` for that state; current finding `<details>`, identity comments and current-head metadata remain part of the visible review.
3. Try omission of the resolved-history suffix, then omission of the entire hidden state block, retaining the current visible review. Never serialize a prefix or subset of the finding state as if it were complete. When the state is omitted, subsequent producer parsing must yield absent state (`None`), never an empty-but-complete state snapshot or synthetic resolved finding.
4. After choosing retained history, use remaining capacity for a full history-omission notice; shorten it to a meaningful shorter notice when necessary; otherwise omit it. Preserve the visible review even when it exactly fills the limit. Separators, markup and any retained notice count against the limit. Emit an omission warning with character counts in existing logs, without logging the body or secrets.
5. If history removal leaves visible content exceeding the limit, first try to retain the original summary and verdict by removing ancillary content from recognized producer structure. Preserve the review identity/current-head metadata, introductory and explicit summary text, every complete verdict-bearing row (including security, compliance, verification, risk, merge recommendation and unknown-status rows), and every current finding's complete `<summary>` label and issue text as exact source spans. Remove recognized optional tool-usage trailers first, then source excerpts after `</summary>` inside current finding details, then recognized non-verdict metadata rows for estimated review effort, test presence, contribution time estimate and priority-file lists. A metadata row is removable only when its entire structure is producer-recognized and contains no nested summary, verdict or status evidence; otherwise protect it. Preserve balanced wrappers and all original summaries, including a blocking finding near the end. Do not slice summaries, rewrite verdict wording, discard a status-bearing row or infer approval from a surviving prefix. If the protected original summary/verdict content and required markup fit, publish that reduced review, using only leftover space for a shortened/omitted notice, and record the removed ancillary content in logs. The original and reduced complete reviews must have identical outcomes under the unchanged classifier.
6. Use a bounded diagnostic requiring manual review only when the protected original summary/verdict cannot fit, the layout cannot be safely recognized, or an oversized body's state is malformed, duplicated or unsupported. Keep provider-generated identity/head metadata that fits and the diagnostic text; do not copy a sliced verdict-bearing model section that could hide a blocker. The existing classifier must escalate this diagnostic; log the reason and counts. This is the fail-closed path when original verdict retention is impossible or unsafe, after the preservation attempt in rule 5, not the default for an oversized visible body.
7. Apply the contract at the final GitHub create/edit limiter, after persistent-update metadata insertion. The early composer hook only defers the cap. Non-review limiter calls retain their original behavior.

These conditional obligations govern only oversized review publications from the pinned GitHub runtime. Unit and mocked-create/edit tests discharge them before the implementation PR opens; the real-image smoke test confirms hook binding and producer parsing before readiness.

### Reversal and History Recovery

To reverse an adopted runtime patch, create a normal follow-up PR from the current integration base that restores the workflow action and environment baseline from the Verification Log. Restore the previous runtime route and undo the added shared-helper sync entry together; verify that the restored route no longer requires the helper. Preserve published history and use ordinary review/CI gates; do not reset, force-push, delete branches or run a release during reversal.

An edited persistent comment does not contain the history or source excerpts the patch omitted. They cannot be reconstructed from that edited body or count-only logs. Recovery requires a separately retained pre-edit copy; without such a copy, rerun a full review to establish current findings and treat prior omitted history as unavailable. Do not claim that rerunning recovers the historical findings or that the omission resolved them. A newly posted comment leaves any separate earlier comment available unless another existing provider behavior later replaces it; no new archive or deletion behavior is planned.
