## Summary

Implement a read-only, operator-invoked worker preflight that validates the selected hub and all configured products, performs bounded GitHub visibility probes, and emits a result the operator can provide to a bounded run. Update the Cursor command and documentation surfaces to require that current result before worker-hub mutations. Complexity: M, because configuration, Git identity, sanitized subprocess failures, documentation gates, and realistic negative tests interact. Dependencies: merged #1462, #1378, #1720 and this spec; Git and authenticated `gh` on the worker. No database, application API, UI, new credential store, or new service is introduced.

## Implementation

Conditional obligations in this section bind to and are discharged at the sites in [Rule 6 Scoped Obligations](#rule-6-scoped-obligations).

1. Add `scripts/development-workflow/hub-worker-preflight.py` with `--hub-dir`, `--worker-dir`, and `--run-id` required. The first two identify the operator-selected hub and worker directory; the run ID binds the result to the bounded invocation. Reject missing/empty/invalid values without echoing arbitrary supplied text. The operator runs this on the worker as the same OS user/environment as the bounded run.
2. Resolve both directory paths physically and require both to identify the same Git worktree root: `git -C <dir> rev-parse --show-toplevel` must succeed and resolve to each supplied directory, and the roots must match. Do not accept a parent, subdirectory, bare repository, or unrelated nested checkout as the hub. Require the hub's workflow mode to be `workflow_hub` using the existing resolver. Worktrees with `.git` files are valid.
3. Use the existing resolver's `list-product-repos --json` and, for every name, `validate --repo <name> --require-local --json`. Reject an empty list, malformed output, unresolved mapping, missing/non-directory checkout, or checkout whose physical Git top-level is not the resolved product path. Do not use `hub-status.sh` as a checkout validity oracle: it checks for `.git` directories and may print remote URLs. Read resolver output internally, never print the local YAML or raw resolver output.
4. Determine the hub GitHub repository from its `origin` via `git remote get-url origin` and the existing resolver's GitHub URL normalization; require a valid, non-credential-bearing GitHub identity. Use each product's resolver-provided `TARGET_GITHUB_REPO` or normalized `git_url`, reject missing or unsupported identity, and verify each checkout's origin resolves to the configured identity. Avoid displaying remote URLs or raw stderr. Probe `gh auth status` and `gh repo view <owner/repo> --json nameWithOwner` for the hub and every product. Use argument arrays, never a shell, disable interactive prompts, bound each subprocess with a finite timeout, and fail on timeout, errors, malformed data, mismatched identity, unavailable authentication, or inaccessible repo. A successful read probe is not a write-permission or Git transport guarantee. Do not invoke the label-creating product preflight, `git fetch`, or credential setup.
5. Emit a stable, machine-readable JSON result with overall pass/fail, selected hub identity, run ID, UTC check time, and outcome for worker directory, each local product checkout, and each GitHub repository probe. Failure includes a fixed check identifier, affected product ordinal when known, and actionable remediation; never emit configured product names or repository identities verbatim. The ordinal is one-based in the shared configuration’s `workflow_hub.product_repos` list order, fixed before per-product validation; do not renumber after a failure. The runbook tells the operator to inspect that numbered shared entry and its corresponding local mapping privately; the agent must not print either configuration. If the list cannot be read reliably, report a configuration-level failure without an ordinal; no raw paths from local configuration, remote URLs, command stderr, tokens, or private YAML in diagnostics. Only emit success after every required check passes. Keep optional dirty/sync warnings out of this implementation. The command never changes local or remote workflow state.
6. Update `.cursor/commands/run-item.md`, `.cursor/commands/run-items.md`, and `.cursor/commands/run-epic.md`: for an operator-identified My Machines / Remote Control hub run, request the operator-run command and its successful result for the current run, use the read-only result verifier below to check run ID, selected hub, timestamp/order, expected products and every required check outcome before the first local or remote workflow write, and stop with correction if missing, malformed, stale, mismatched, or failed. The run ID and timestamp are operator-supplied evidence, not cryptographic proof. Read-only checkpoints retain existing rules. Other targets and non-hub runs keep existing behavior. Keep the existing dispatch profile declaration independent; no target autodetection.
7. Update `docs/workflow/development-workflow/integrations/cursor-my-machines.md` and `cursor-dispatch-profiles.md` with the same operator-invoked gate, an example for `--worker-dir`, result contents, local-output confidentiality, and the limits of read-only access. Remove the obsolete #1721-pending text. Add a changelog fragment and cover any newly added template-owned files through `sync-manifest.yaml` as required by the coverage checker.

## Result Schema and Verification

Conditional obligations in this section bind to and are discharged at the sites in [Rule 6 Scoped Obligations](#rule-6-scoped-obligations).

Preflight success emits one JSON object with `schema` equal to `hub_worker_preflight.v1`, `result` equal to `pass`, a UUID `run_id`, UTC `checked_at`, `hub_repo_id`, `hub_checkout_id`, `config_id`, `worker` equal to `pass`, `hub_github` equal to `pass`, and a nonempty `products` array. Each product object has a unique `product_id` (SHA-256 of its UTF-8 configured name), `repo_id` (SHA-256 of the normalized GitHub identity), `checkout` equal to `pass`, and `github` equal to `pass`. The hub identity is represented by the same normalized-identity SHA-256 in `hub_repo_id`. These are comparison identifiers, not secrets or authentication; hashes can be guessed. Never print the raw name or remote identity. A failure emits `result` equal to `fail` and a safe diagnostic; it is never accepted as success. Reject missing or unknown schema, missing or extra keys, wrong types, duplicate product names, malformed timestamp, unknown status and incomplete entries. Require the run ID to be a canonical UUID generated for the run; never echo rejected input.

`hub_checkout_id` is SHA-256 of the UTF-8 canonical physical hub root path, computed locally. It distinguishes same-origin clones and linked worktrees; it is an opaque comparison identifier, not a secret or authentication mechanism and may permit path guessing. Do not print the path. `config_id` hashes a canonical serialization of sorted tuples of configured product name, normalized GitHub identity, and SHA-256 of each canonical local checkout path; never hash or expose raw local YAML or credentials. Reject duplicate product names and missing values before hashing. Recompute both identifiers, the normalized GitHub identity from the current hub origin, and the expected product-name/identity set from the current selected hub configuration on the worker during verification. Reject a missing, unsupported, credential-bearing or changed hub origin, or a `hub_repo_id` value that differs from the hash of the recomputed origin. Hash the independently resolved product names and normalized identities, compare the exact product-ID/repository-ID pairs to the result, and reject omissions, additions, duplicates, mismatched identities or config/checkout fingerprints.

Provide a read-only verifier mode on the same command accepting the result, selected hub, run ID, and operator-recorded run-start and hub-selection UTC timestamps. The operator asserts hub selection occurred at or after run start; a missing, invalid, future or ambiguous selection timestamp fails before result acceptance. It validates the schema, result, current hub/config fingerprints, exact product set, matching run ID and a parseable check time at or after both run start and hub selection and not in the future; any uncertainty fails closed. It does not repeat network access, authenticate the operator or protect against forged JSON. Require invocation from the same worker environment, and treat a changed checkout mapping as invalidating the result. The three command entrypoints require verifier success before writes. Test two hub worktrees sharing an origin but differing in path or mapping; omission, addition, duplicate, malformed, wrong-identity and stale result cases; unchanged config; valid different product ordering, a pre-selection result, missing or ambiguous selection time, and a changed or mismatched hub origin. No network or workflow writes occur in verifier mode.

## Decision and Evidence Contract

Conditional obligations in this section bind to and are discharged at the sites in [Rule 6 Scoped Obligations](#rule-6-scoped-obligations).

For the three named Cursor bounded entrypoints, a worker run proceeds to its existing mutation gates only when the operator asserts a matching current-run, current-hub successful result with all required outcomes. Missing input, unavailable or incomplete result, mismatch, stale evidence, any failed or inconclusive probe, and unknown input stop before mutation. The preflight itself checks a single operator-selected hub and all configured products per invocation; no prior invocation's result is reusable. An explicit warning-only result is not required in this implementation. The entrypoints cannot authenticate a pasted result; they must not claim automatic enforcement beyond the operator assertion. Read-only work and non-worker contexts do not call the preflight. Existing dispatch, reviewer, CI, and checkpoint gates remain separate.

### Parser-risk edge cases and unit mapping

The preflight consumes structured JSON returned by the existing resolver and `gh`, so parser-risk applies. The focused test suite maps each of these to an automated case: empty, truncated, non-object, missing-key, wrong-type, and extra-field JSON; names containing spaces, control characters, or planted secrets (raw names must never appear); empty, malformed and credential-bearing GitHub identities; multiple product entries including a later failing entry; and duplicate or nested configuration rejected by the existing resolver. The implementation delegates YAML parsing and URL normalization to existing resolver code rather than inventing a new grammar. Inline suppressions are not supported.

The selector discovers top-level `test-*.sh` suites in `scripts/development-workflow/select-test-suites.sh`; add explicit `# covers:` mappings for the new production script and affected command surfaces and verify selector output rather than relying on a default association.

## Risks and Mitigations

- Sensitive diagnostics: suppress untrusted subprocess output; test credential-bearing URLs and private values, including a sensitive configured product name, as planted sentinel strings in success and failure cases.
- Wrong checkout or inaccessible host: compare actual Git roots and origin identities, fail closed on every unresolved probe, and keep timeout bounded.
- Operator assertion can be false: explicitly state the trust boundary; do not describe output as tamper-proof or as automatic environment detection.
- Config drift: repeat the preflight per bounded run; record result time and scope.
- Regression to non-worker execution: test the three command surfaces and document unchanged paths for other targets.

## Rule 6 Scoped Obligations

The local path and remote identity checks govern every configured product entry and the hub, discharged in the preflight before success. The schema, timestamp, origin, product-set, and evidence checks govern the verifier for every worker preflight result and the three named Cursor entrypoints for operator-identified worker hub runs; verifier validation is discharged before their first workflow write. Documentation updates govern the two named integration documents and three named entrypoints at implementation review; tests cover those same surfaces and both preflight and verifier modes. The read-only exemption governs all checkpoints that perform no workflow writes; existing profile rules still apply there.
