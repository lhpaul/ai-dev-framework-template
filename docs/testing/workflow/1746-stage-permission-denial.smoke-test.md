Run against the implementation PR checkout. Use only fabricated reports and temporary consumer configuration. Do not change real credentials, permissions, product checkouts, or live PR state to create a denial. The automated fixtures verify the documented boundary; they do not establish how every real harness formats an error.

1. Run `bash scripts/development-workflow/tests/test-stage-role-permission-denial.sh` and `bash scripts/development-workflow/tests/test-check-sync-manifest-coverage.sh`. Expect both to pass, including the list-membership and no-bypass cases. Run the plan's named existing regression and lint suites as part of implementation validation.
2. In the focused fixture, supply a fabricated report from a reachable implementation stage role that explicitly identifies a denied tool or local path. Expect the affected item to stop with `stage_role_tool_or_path_denied`, item and stage, known action or target, and a concrete operator correction; no inline product work, approval, completion, or `needs-fixes` label may result solely from the denial.
3. Repeat with a review role, including the Step 7a CLI-review path. Expect the review gate to remain failed or incomplete, the denial stop to be reported, and a fresh successful review to be required after correction.
4. Supply a credential-only denial, an unreachable stage role, an unclassifiable access refusal, a generic non-denial tool error, and both independently established tool and credential causes. Expect the approved decision matrix's distinct paths: existing credential and handoff stops, `unclear_requirements` for an unclassifiable refusal, existing generic-error handling, and both applicable stops for established mixed causes.
5. Simulate a confirmed denial with an uncertain remote effect. Expect the denial stop to remain, a durable-state reconciliation before retry, and dependent work to stay held. After a simulated operator correction and reconciliation, the same owning role resumes; a new context starts a fresh run with a profile declaration. A repeated denial stops again without an automatic retry loop. A separate Work Item Runner denial retains Protocol 90's boundary-specific behavior.
6. In a disposable consumer `.ai-dev-workflow.yaml`, declare `guardrails.stop_conditions` without the new name but put that name in a comment or unrelated field. Run the sync coverage checker with that consumer as `--consumer-root`: expect `REQUIRED_ADDITION_MISSING` and exit 1. Add the exact name to the declared list and rerun: expect `REQUIRED_ADDITION_PRESENT` and no missing-addition finding. Check malformed and wrong-type declared lists fail with a sanitized diagnostic, and that legacy manifest entries retain their prior behavior. Record the fixture path, line, commands, statuses and reviewed head in the implementation PR.
7. Inspect the current Protocol 90/91/95, role, command, profile and guardrail surfaces and #1462 smoke Step 10. Expect the new stage-role stop and recovery to agree across current normative guidance, with historical spec files left as history. Re-run the plan's live inventory query and record how each match was handled.
