- Readiness labels (`ready-for-human-review`, `ready-for-regression`) can no longer be applied on an agent's judgement alone. The new `scripts/development-workflow/apply-readiness-labels.sh` refuses to apply either label unless every configured ready-phase reviewer check run is `completed` for the current head SHA, the reviewer posted no blocking findings on that SHA, and no non-reviewer check is pending or failing. An absent reviewer check run counts as **not** clean, so a reviewer that refused to run never reads as a clean verdict; a `neutral` Bugbot check run paired with a usage/spend-limit notice is refused the same way (`REASON=reviewer-unavailable`), because Bugbot reports both a quota refusal and a restricted-access refusal through that shape; and for every **non-Bugbot** ready-phase platform a completed check run concluding `neutral`, `cancelled`, or `skipped` is refused fail-closed as `reviewer-unavailable` — only Bugbot can clear such a conclusion (via its notice probe), so no other platform's non-review can read as clean. Findings come from `pulls/N/comments` and `pulls/N/reviews`, never from issue comments; the only issue-comment read is that availability probe. A configured ready-phase reviewer whose check-run name has no mapping (for example `codex-github`) is refused as `REASON=reviewer-check-name-unresolved` instead of being silently skipped, so a platform without a mapping never means zero reviewer verdicts behind the label. The head SHA is re-fetched immediately before the label mutation and again after it, and any drift refuses (`REASON=head-changed-before-apply`, or escalates `head-changed-after-apply`) because `--add-label` binds no commit. All paginated `gh api` reads use `--slurp` and flatten pages in jq, so a first-page failed reviewer check can never be corrupted into a passing verdict. The reviewer leg applies to implementation branches only (`feature/*`, `fix/*`, `refactor/*`, `hotfix/*`, `backport/hotfix/*`), the same boundary Protocol 91 draws for `IS_IMPLEMENTATION_PR`: ready-phase reviewers are not dispatched on spec, implementation-plan, graduation, or release PRs, so gating on a check run would refuse every doc-stage and release PR.
- `ready-for-human-review` refuses while a non-reviewer check is still pending; `ready-for-regression` does not, because that label is what *starts* the configured regression workflow and gating it on pending checks would deadlock Step 7b against the checks the label itself triggers. A failing check refuses under either label.
- Protocols 91 (Step 7b, Step 8a), 95 (Step 8), 03 (all four paths), and 90 (Step 5.1) now state that agents must not call `gh pr edit --add-label ready-*` directly and must route readiness through the helper, whose `RESULT=refused` verdict is a stop rather than a warning. Protocol 05 keeps the direct apply for release PRs and documents that exemption, since release branches never carry a reviewer check run. The three `sync-template` command/skill mirrors point at the helper too.
- `workflow-lib.sh` gains `normalize_status_check_rollup()` (the `statusCheckRollup` duplicate-collapsing normalization `pr-review-loop.sh` and `pr-ci-loop.sh` each carried inline) and `bot_login_for_platform()`, so readiness gating and the completion self-check resolve reviewer logins from one place. No existing caller is changed by either addition.
- `scripts/development-workflow/tests/test-apply-readiness-labels.sh` covers the gate, including two planted failing cases: a reviewer with no check run for the current head, and a `neutral` Bugbot check run carrying a usage-limit notice. Both are refused rather than labelled. Further planted cases lock the three PR #1818 Codex findings: a ready-phase platform with no check-name mapping, head drift on either side of the label mutation, and a reviewer verdict split across `gh api --paginate` pages.
- The five PR #1818 Codex review findings are fixed: the ready-phase reviewer list is now read from the target PR head's own `.ai-dev-workflow.yaml` (base64-decoded via the contents API), and an unreadable head configuration escalates `REASON=ready-config-unreadable` instead of silently falling back to the local checkout, so a PR that removes its configured reviewer can no longer be labelled with zero reviewer gates; post-apply head drift (`head-changed-after-apply`) now removes the label it can no longer certify before escalating, so the new unreviewed head does not carry it; reviewer and inline-comment findings are time-bounded to the selected check run's `started_at`, so a stale same-SHA comment from an earlier reviewer run no longer blocks forever; `pr-review-loop.sh`'s regression-label auto-restore routes the mutation through the helper instead of a bare `gh pr edit --add-label` (helper failure keeps the documented fail-open WARN-and-proceed); the clean-path Step 7b summary no longer hands agents a copy-paste `gh pr edit --add-label "ready-for-regression"` command — it now points at the helper invocation, so the instruction cannot bypass the gate it exists to enforce; and the helper is declared in `sync-manifest.yaml` and the product-repo skeleton manifest so routed product repositories receive it. A round of three further Codex findings on PR #1818 is fixed: an implementation PR whose head configuration resolves an empty ready-phase reviewer list (for example a PR that removes `review.on_ready.github`) now refuses as `REASON=reviewer-policy-empty` instead of applying the label with zero reviewer gates — the helper reads the PR base branch's configuration (resolved from the PR `baseRefOid`) and only permits an empty head list when the base policy is empty too (union of base and head policies; an unreadable base configuration escalates `base-config-unreadable`); the reviewer check-run conclusion is now an explicit allow-list — `success` is clean, `failure`/`action_required`/`timed_out`/`startup_failure` block, `neutral`/`cancelled`/`skipped` keep their unavailable handling, and any other non-empty conclusion (such as `stale`) refuses fail-closed as `REASON=reviewer-check-unknown-conclusion` with the conclusion named in `REVIEWER_REPORT`, mirroring `run_ronda_review()`; and `pr-review-loop.sh`'s regression-label restore path no longer discards the helper's stderr, so its actionable WARN output (including the head-drift "label remains attached, remove manually" warning) is observable.
- A round of three further Codex findings on PR #1818 is fixed: for implementation PRs the base-branch ready-phase policy is now ALWAYS fetched and the gate validates the deduplicated **union** of base and head platforms — previously the base policy was only consulted when the head list was empty, so a PR that *replaced* a base-configured reviewer (base `bugbot` -> head `ronda`) never fetched the base config and silently waived the base-configured reviewer; the pre-apply revalidation no longer re-checks only `headRefOid` — it re-fetches the reviewer check runs and the `statusCheckRollup` for the same head and re-applies the same conclusion and pending/failing rules (shared `reviewer_check_conclusion_is_clean()`), refusing as `REASON=reviewer-state-changed` before the label mutation when a rerun (success -> pending/failure) made the verdicts stale; and every post-mutation escalation path (`label-verify-failed`, `label-not-applied`, a failed post-apply `pr view`, `head-changed-after-apply`) now attempts a best-effort `gh pr edit --remove-label` through the shared `remove_readiness_label_best_effort()` helper before escalating, so no unverified readiness label stays attached to the PR.
- A round of three further Codex findings on PR #1818 is fixed: the pre-apply revalidation now fails closed — a failed or empty revalidation check-run fetch escalates `REASON=revalidation-unreadable` instead of returning success and applying the label from a potentially stale verdict; a same-SHA reviewer rerun that starts after the initial finding scan and completes before revalidation is no longer accepted on its conclusion alone — the revalidation rescans the full finding surfaces (`pulls/N/comments`, `pulls/N/reviews`, both via the shared `count_reviewer_blocking_findings()`) and the Bugbot availability-notice probe (shared `bugbot_unavailable_notice_present()`) against the newly selected check run's timestamp, because a rerun can conclude `success` while posting blocking comments that only belong to the new run; and the required ready-phase reviewer set is now the BASE-branch policy instead of the round-5 base∪head union — `pr-review-loop.sh` dispatches ready-phase platforms from the base configuration, so a head-only ADDED reviewer never runs and requiring its check run would permanently refuse `reviewer-check-absent`; a head that removes or replaces a base reviewer still cannot waive it (the base platform is gated regardless), and head-only additions are validated when present-with-a-run but never required.
- A round of three further Codex findings on PR #1818 is fixed: `hotfix/*` head branches are now exempt from the reviewer leg exactly as `release/*` branches are — `pr-review-loop.sh`'s `_check_release_pr_guard` never dispatches the reviewer loop on a hotfix, so requiring a reviewer check run permanently refused both readiness labels `REASON=reviewer-check-absent`; the CI leg still applies on hotfix PRs (the same handling release branches get), and `backport/hotfix/*` stays reviewer-gated; the base-branch ready-phase policy is now resolved with local review overrides applied (`WORKFLOW_APPLY_LOCAL_REVIEW_OVERRIDES=1`, the same effective-policy resolution the loop uses to dispatch), so a local `.ai-dev-workflow.local.yaml` that replaces `review.on_ready.github` no longer leaves the helper waiting for a shared-config reviewer check the loop never dispatched — an absent override file (gitignored, not copied into agent worktrees, #1817) falls back to the shared policy exactly as the loop itself does in a worktree; and the test fixtures' base64 encoders pipe through `tr -d '\n'` (portable across BSD and GNU) — GNU coreutils `base64` wraps at 76 columns by default, which embedded literal newlines in the JSON `content` strings and failed the suite on Linux with `ready-config-unreadable` / `base-config-unreadable`.
- A round of three further Codex findings on PR #1818 is fixed: a rerun of the helper on a PR that ALREADY carries the requested label (for example after a same-SHA reviewer rerun or a new push) no longer leaves that stale label attached on a pre-apply refusal — every refusal path now routes through a shared `refuse()` exit that removes the already-present label best-effort (WARN-and-refuse on removal failure, and no removal when the label was not already present), so a `RESULT=refused` verdict can no longer coexist with a readiness label the delegated and batch merge gates would consume as an all-clear; the pre-mutation head recheck now runs AFTER the reviewer-finding rescan and the CI revalidation (the several-API-call window a push can land in), immediately before `gh pr edit --add-label` — previously it ran before those revalidations, so a push landing during them labelled the new unreviewed head `REASON=head-changed-before-apply`-free — and that final guard repeats the revalidation rescan, so a blocking comment posted after the revalidation rescan still refuses before the mutation; and the Bugbot availability-notice time-boundary filter (the only strict `>` left) is now inclusive `>=` like every other timestamp filter in the helper, so a notice created in the same second as the check run's start no longer reads as clean on a `neutral` run (`REASON=reviewer-unavailable` fires instead).
- A round of three further Codex findings on PR #1818 is fixed: `escalate()` now strips a pre-existing readiness label before escalating — previously only `refuse()` did, so a rerun on an already-labelled PR that hit an API or parse failure (`revalidation-unreadable`, `check-run-fetch-failed`, ...) exited 2 with the stale label still attached for the merge gates to consume (removal is attempted only when the label presence was actually captured at run start, so a `pr-state-unavailable` never fires a blind removal); the pre-apply checks now run as ONE strictly ordered final block — reviewer revalidation and finding rescan, then the CI re-read, then the final `headRefOid` comparison as the last API call before `gh pr edit` — previously the final head check sat before the finding rescan (reopening the push race) and the CI state was read before the rescan without a repeat after it, so a CI rerun to pending/failure during the rescan window was missed, and unlike head drift the post-apply verification cannot catch it.
