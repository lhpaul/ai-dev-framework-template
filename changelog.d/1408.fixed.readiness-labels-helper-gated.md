- Readiness labels (`ready-for-human-review`, `ready-for-regression`) can no longer be applied on an agent's judgement alone. The new `scripts/development-workflow/apply-readiness-labels.sh` refuses to apply either label unless every configured ready-phase reviewer check run is `completed` for the current head SHA, the reviewer posted no blocking findings on that SHA, and no non-reviewer check is pending or failing. An absent reviewer check run counts as **not** clean, so a reviewer that refused to run never reads as a clean verdict; a `neutral` Bugbot check run paired with a usage/spend-limit notice is refused the same way (`REASON=reviewer-unavailable`), because Bugbot reports both a quota refusal and a restricted-access refusal through that shape. Findings come from `pulls/N/comments` and `pulls/N/reviews`, never from issue comments; the only issue-comment read is that availability probe. The reviewer leg applies to implementation branches only (`feature/*`, `fix/*`, `refactor/*`, `hotfix/*`, `backport/hotfix/*`), the same boundary Protocol 91 draws for `IS_IMPLEMENTATION_PR`: ready-phase reviewers are not dispatched on spec, implementation-plan, graduation, or release PRs, so gating on a check run would refuse every doc-stage and release PR.
- `ready-for-human-review` refuses while a non-reviewer check is still pending; `ready-for-regression` does not, because that label is what *starts* the configured regression workflow and gating it on pending checks would deadlock Step 7b against the checks the label itself triggers. A failing check refuses under either label.
- Protocols 91 (Step 7b, Step 8a), 95 (Step 8), 03 (all four paths), and 90 (Step 5.1) now state that agents must not call `gh pr edit --add-label ready-*` directly and must route readiness through the helper, whose `RESULT=refused` verdict is a stop rather than a warning. Protocol 05 keeps the direct apply for release PRs and documents that exemption, since release branches never carry a reviewer check run. The three `sync-template` command/skill mirrors point at the helper too.
- `workflow-lib.sh` gains `normalize_status_check_rollup()` (the `statusCheckRollup` duplicate-collapsing normalization `pr-review-loop.sh` and `pr-ci-loop.sh` each carried inline) and `bot_login_for_platform()`, so readiness gating and the completion self-check resolve reviewer logins from one place. No existing caller is changed by either addition.
- `scripts/development-workflow/tests/test-apply-readiness-labels.sh` covers the gate, including two planted failing cases: a reviewer with no check run for the current head, and a `neutral` Bugbot check run carrying a usage-limit notice. Both are refused rather than labelled.
