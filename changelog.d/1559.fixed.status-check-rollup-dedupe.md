- **Every CI consumer now judges only the latest run of each check** (#1559): GitHub keeps superseded runs in both `statusCheckRollup` and the REST `commits/<sha>/check-runs` response. The REST default `filter=latest` means latest per check suite, and another run of a workflow reports in a new suite. A check that failed and then passed on re-run (PR #1547: `policy failure 05:26:31`, `policy success 05:28:16`) could therefore read as a current failure.
  - The deduplication now lives in one place, `STATUS_CHECK_ROLLUP_DEDUPE_JQ` / `normalize_status_check_rollup` in `workflow-lib.sh`. It replaces three inline copies and two divergent implementations.
  - Consumers routed through it: `pr-ci-loop.sh`, `pr-review-loop.sh` (the CI baseline plus the Ronda, Bugbot, Devin, and PR-Agent check-run probes), `item-completion-self-check.sh`, `batch-merge.sh`, `discover-workflow-state.sh`, `apply-readiness-labels.sh`, `haystack-reviewer.sh`, `run-epic-risk-classifier.sh`, and `run-epic-delegated-gate.sh`. It is also used by Protocol 91's Step 8a Check 0 readiness snippet.
  - The delegated merge gate and the Step 8a readiness gate no longer block a healthy PR on a superseded failure.
  - REST check runs carry no workflow name, so the new `latest_check_runs_for_sha` (used by the Step 8a Check 0 readiness count) first tags each run with its workflow file (via `actions/runs?head_sha=`). Same-named jobs of different workflows stay separate.
  - The risk classifier no longer merges same-named jobs from different workflows, which could hide one workflow's failure behind the other's success.
  - A queued re-run now counts as the latest run instead of sorting behind the result it replaces.
  - Protocols 90 and 91 now state that "0 non-green checks" counted over the raw rollup is not a readiness assertion.
