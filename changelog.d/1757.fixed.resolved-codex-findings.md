- **Reviewer loop no longer counts resolved Codex findings as current blockers** (#1757): `pr-review-loop.sh` and `codex-github-reviewer.sh` now share one applicability-aware Codex review-thread counter (`codex-github-evidence-lib.sh`) that excludes resolved, outdated, dismissed-review, and non-live-head-commit threads from blocker counts. The shipped `unresolved_count=1` floor that forced a blocker count of at least one — even when a strict recount confirmed zero applicable unresolved threads — is removed; a historical Codex finding that is merely still visible now yields `waiting_on_reviewer` (a fresh-review request) instead of a stale `needs_fixes`. Acknowledgement-only evidence (a thumbs-up reaction with no submitted review) now exits `4` (`WAITING_ON_REVIEWER`) instead of `2` (escalate), and an account-not-connected hard stop keeps its own `REASON=codex-github-account-not-connected` instead of being mislabelled as a usage limit.
- **Codex marker well-formedness, finding/thread correlation, and four new fail-closed escalations** (#1757): a root PR comment's `Reviewed commit` marker is now classified for well-formedness (empty/non-hex/multiple-token/interior-substring/superstring rejection, plus locally provable ambiguity) and, for a triggered live head, filtered by the head's evidence window (the freshness boundary already enforced server-side by the poll queries). A blocking finding's own review-thread correlation is now checked before it can produce `needs_fixes`: a root-comment finding, or a review's own body finding, always lacks a stable thread identifier and now escalates `codex_finding_thread_correlation_missing` instead of routing to fixes; a fully cleared verdict (every inline finding resolved, no other applicable unresolved conversation) now waits for a fresh review instead of escalating or dispatching a fixer. A current terminal verdict that reproduces neither an approved template nor the documented blocking markers now escalates `codex_current_verdict_unrecognized` instead of the previous "unrecognized response format — safe-fail" `NEEDS_REVISION`. A bounded evidence-query failure now escalates `evidence_unavailable_codex_thread_state`. The reviewer-loop cycle cap (`reviewer_loop_cap_exceeded`) now also applies to a `waiting_on_reviewer` result (including the cleared-findings retrigger path), not only `needs_fixes`/`needs_rerun`, so an exhausted allowance always escalates for human review rather than waiting indefinitely.
- **A live-head `CHANGES_REQUESTED` review is no longer silently remapped to `waiting_on_reviewer`** (#1757): `pr-review-loop.sh`'s exit-1 recount (the same recount that lets a merely-visible, fully-resolved historical finding wait for a fresh review instead of reporting a stale `needs_fixes`) previously trusted a zero-thread count on its own, even when the companion's `NEEDS_REVISION` verdict came from a live-head Codex review whose GitHub review state is `CHANGES_REQUESTED` — a structured blocker that is not itself a thread and is never cleared by resolving conversations (spec Business Rules 5/6). A body-only `CHANGES_REQUESTED` review, or one whose own inline threads are all separately resolved, now still reports `needs_fixes`; the recount only remaps to `waiting_on_reviewer` once a live-head-review check (`codex_current_head_changes_requested_blocker`, in the shared evidence library, fail-closed on any lookup failure) confirms no such review is active.
- **Live-head evidence-window occupancy guard closes the SHA-reuse gap, for both a triggered and a trigger-less live head** (#1757): a live head's evidence window now additionally requires that a candidate root comment's occupancy — not just its revision — match the live head, so a SHA that occupies the pull request's head position twice (a revert, or a force-push back to a previously reviewed commit) can no longer have its first-occupancy clean evidence silently authorize readiness for the second. The occupancy boundary is raised past either newer terminal evidence naming a different SHA, or a `head_ref_force_pushed` / `head_ref_deleted` / `head_ref_restored` pull-request timeline event (paginated, not filtered by the event's own `commit_id`) that postdates the boundary's anchor; a comment must satisfy this boundary strictly, with no comment-ID tiebreak. A triggered live head anchors on its own latest trigger; the trigger-less pre-check path (the common case when Codex's GitHub App auto-reviews a push before this workflow posts its own trigger comment) has no trigger of its own yet and anchors on the pull request's creation time instead, closing a reviewer-reproduced false clean where a stale marker-pinned clean comment for a reused SHA, an intervening comment naming a different SHA with real findings, and a reverted head with no new trigger posted previously returned `VERDICT: APPROVED`. A timeline read that fails or is truncated after one retry escalates `evidence_unavailable_codex_thread_state` (the same fail-closed "boundary unreadable" contract already used elsewhere in this item) rather than silently skipping the guard, for either path. The trigger-less pre-check's submitted-review evidence (`pulls/{pr}/reviews`) had the same unguarded gap as its root-comment evidence — GitHub's Reviews endpoint returns every review ever submitted for the pull request, so a clean review submitted during an earlier occupancy of the live head SHA could still be selected as evidence for a later occupancy of that same SHA — and is now floored by the same occupancy boundary (or, absent any boundary event, the pull request's creation time); the four triggered-path review queries were already occupancy-safe by construction (`submitted_at` bounded by their own trigger) and needed no change.
